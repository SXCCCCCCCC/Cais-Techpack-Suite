# 第 1 步「从虚空中来」调研

设计见 `设计流程.md` §1。本文是 2026-09-18 的逐台查证结果，用于实现「挖掘时按概率出远古奖杯残片」。

> **2026-09-18 订正说明**：初版有三处结论经字节码复核后被推翻，正文已就地改正并标注（§1 / §2.3 / §2.4 / §2.5 / §2.2）。
> 摘要如下：
> 1. **Create OE 不是「按权重挑一个」**，是**各自独立掷骰** → 加残片是纯额外，不是替换（§2.3）
> 2. **IE 矿脉是数据包 JSON**（`immersiveengineering:mineral_mix` 是正式 recipe type），不是代码注册（§2.4）
> 3. **IU 有数据层路径**（`industrialupgrade:quantum_quarry` 配方类型），只是概率池内均匀、调不到 0.1%（§2.5）
> 4. 另补一条初版没写到的硬限制：**IF 的 `weight` 是 int**，不重标定现有配方的话 0.1% 达不到，下限 0.34%（§2.2）

## 0. 设计意图与实现语义

- **概率**：0.1%（备选 0.01%）
- **语义 = 替换**：触发时不填充那次的正常产物，改成给残片（不是"额外多给一个"）。
  ⚠️ **2026-09-18 订正**：五台里只有 IF 镭射钻能真正做到「替换」（它是按权重挑一个）；
  其余四台都是独立掷骰型，加一条就是纯额外。见 §1 与 §2.3。
- 玩家视角的表述是「每次挖掘都有概率出残片」

**数值核算**（第 5 步的 Create 路线要 43 个残片）：

| 概率 | 需要挖掘次数 | 实际体感（按虚空矿机/镭射钻的速率） |
|---|---|---|
| 0.1% | 43,000 | 几十分钟到几小时 ✓ |
| 0.01% | 430,000 | 十几到几十小时 ✗ |

结论：**0.1% 合理，0.01% 会变成纯挂机**。

## 1. 「替换」在两种产出模型下的差别（关键）

| 产出模型 | 机器 | 加一条 0.1% 的实际效果 |
|---|---|---|
| **按权重挑一个**（每次只出一样东西） | IF 镭射钻 | **真正的替换** ✓ —— 那次出的就是残片，矿石没了 |
| **各自独立掷骰**（多个产物各 roll 各的） | GT 虚空采矿机、Create OE、IE 斗轮挖掘机 | **额外多给** ✗ —— 矿石照出 |
| **在产出点追加**（不属于上面两种） | IU 量子采石场 | 等价于「额外」，见 §2.5 |

> **2026-09-18 订正**：原表把 Create Ore Excavation 归到「按权重挑一个」，实测是错的。
> `DrillBlockEntity.onFinished` 对 `output` 里每一项**各调一次** `ProcessingOutput.rollOutput()`，
> 命中者全部入队 —— 是**独立掷骰**。详见 §2.3。

两种模型的**残片产量完全一样**（都是 0.1%），差别只在玩家是否亏掉那 0.1% 的矿。
是否要在后者里人为制造损失（把矿石概率乘 0.999）→ **建议不造**：0.1% 的矿损失玩家无感，而代码是白添的复杂度。

## 2. 逐台机器

### 2.1 GT 虚空采矿机（KubeJS 注册的机器）

| 项 | 内容 |
|---|---|
| 机器来源 | KubeJS 注册（`gtceu:void_miner` + `world_data_scanner`），Java 侧无类可引用 |
| 产出配置 | `kubejs/server_scripts/gtceu_void_miner.js` |
| 产出机制 | GT builder：`recipe.chancedOutput(item, 概率, boost)`，概率单位 **1/10000**；包内按「权重 2~10、chance = 权重/本脉权重和」写，每次挖 1 个；世界三份（主世界/下界/末地）各一段 |
| 挂点 | 在同一段里加 `recipe.chancedOutput('gtceu:trophy_fragment_clump', 10, 0)` → 0.1% |
| 语义 | 独立掷骰 → 实质是"额外"（见 §1） |

### 2.2 IF 镭射钻

| 项 | 内容 |
|---|---|
| 产出配置 | `kubejs/server_scripts/gtceu_laser_drill.js`（包内已配 40 条 GT 矿石 + 1 条神秘农业活化水晶） |
| 产出机制 | `industrialforegoing:laser_drill_ore` 配方；条目结构含 `catalyst`（透镜）/ `entity` / `output` / `pointer` / `rarity`（`depth_min`/`depth_max`/`weight`/`blacklist`/`whitelist`）；**按 weight 在稀有度表里挑一个** |
| 类证据 | `com/buuz135/industrial/recipe/LaserDrillOreRecipe.class`（IF jar） |
| 挂点 | 加一条 `weight` 最小的条目 → **真替换**（这是五台里唯一能真替换的） |
| ⚠️ 整数权重限制 | `weight` 是 **int**，且就是同群系同深度下的选择权重（概率 = w_i / Σw）。主世界竞争池约 292，所以 **0.1% 在不动现有配方的前提下达不到**，下限是 `1/293 = 0.34%`。要精确 0.1% 必须把所有竞争配方（含 IF 自带 34 条默认）的权重重标定 |
| 透镜不过滤 | `catalyst` 只影响权重（插对透镜 `+catalystModifier(+8)`），**不做筛选**。所以只需一条配方用 `rarity` 覆盖三个维度，**绝不能按 16 个透镜各挂一条**（等于权重 ×16） |
| catalyst 选择 | 必须填一个**永远不会插进透镜槽**的物品（实现时填的残片自己）。否则 +8 会把权重从 1 顶到 9，掉率翻 9 倍 |
| 实际取值 | 按设计决定**不重标定**，`weight = 1` → 主世界约 0.34%、下界约 0.58%、末地约 3.2% |
| 类证据 | `com/buuz135/industrial/recipe/LaserDrillOreRecipe.class`（IF jar）；权重的选取逻辑在 `OreLaserBaseTile.onWork`（`WeightedRandom.getRandomItem`） |

### 2.3 Create Ore Excavation

| 项 | 内容 |
|---|---|
| 产出配置 | `kubejs/server_scripts/create_ore_excavation.js`（GT 主世界 8 条 / 下界 4 / 末地 2 / IU 10 / 神秘农业 2，共 26 条） |
| 产出机制 | `createoreexcavation:drilling` 的 `output: [...]`。每项是 `{ item, count?, chance?, nbt? }` —— **键是 `chance`，不是 `weight`**；矿脉由 `createoreexcavation:vein` 定义（`placement` + `biomeWhitelist` + `alwaysInfinite`） |
| 掷骰语义 | **各自独立掷骰**。`DrillBlockEntity.onFinished` 对每项各调一次 `ProcessingOutput.rollOutput()`，命中者全部入队 —— 一次可以同时出多件，也可能一件都不出 |
| 挂点 | 往每条 `output` 末尾追加 `{ item: 'gtceu:trophy_fragment_clump', chance: 0.001 }` → **纯额外**，不需要重标定现有 chance |
| 类证据 | `createoreexcavation-1.20-1.6.5.jar` → `com/tom/createores/block/entity/DrillBlockEntity.class`（`onFinished` 的 bootstrap 指向 `ProcessingOutput.rollOutput`）；`chance` 键出自 Create 的 `ProcessingOutput.deserialize` |

> **2026-09-18 订正**：原文写的「每项带权重」「→ 真替换」两条都不对。
> 另外顺带一个**既有影响**：现有各矿脉的 chance 之和恰好 = 1.0（如 `gt_ow_metaloxide_vein`），
> 在独立掷骰下这意味着**约 38% 的概率一件都不出**、偶尔一次出 2~4 种不同矿。
> 脚本头部注释「权重 2~10，chance = 权重/本脉权重和 → 每次挖 1 个」也是按旧的错误理解写的。
> 这一步的掉率设计要不要一起改，另议。

### 2.4 IE 斗轮挖掘机

| 项 | 内容 |
|---|---|
| 产出机制 | `MineralMix`（矿脉混合物）：每个矿各自一条 **独立概率**；矿脉按区块/维度归属（`ExcavatorHandler$MineralSelection`） |
| 公开 API | `blusunrize.immersiveengineering.api.crafting.builders.MineralMixBuilder`（有 `ores(IngredientWithSize, float, ICondition)`）；序列化器 `MineralMixSerializer` |
| 类证据 | IE jar：`MineralMix` / `MineralMixBuilder` / `ExcavatorHandler` / `MineralMixSerializer` |
| 注册方式 | **数据包 JSON**，不是代码注册。IE 10.2.0 把 mineral mix 做成了普通 recipe type（`immersiveengineering:mineral_mix`），**配方 ID = 文件路径**，即 `data/<ns>/recipes/mineral/<name>.json` |
| 挂点 | 覆盖 27 条矿脉（IE 内置 21 + 包内 iu 5 + createaddition 1），各在 `ores` **数组首位**插 `{"chance":0.001,"output":{"item":"gtceu:trophy_fragment_clump"}}`。写进 `kubejs/data/immersiveengineering/recipes/mineral/`——KubeJS 虚拟数据包对同路径是覆盖 |
| 为何必须放首位 | `MineralMix.getRandomOre` 是**累积**判定（`r -= chance; if (r < 0) return`），而 27 条的 `ores` chance 之和**全部 ≥ 1.0** —— 追加到末尾永远轮不到 |
| 路径坑 | 必须镜像 `mineral/`。`kubejs/data/immersiveengineering/recipes/mineral_mix/` 那个空目录产出的是新 ID `mineral_mix/<name>`，会变成多一条按 `weight` 竞争的重名矿脉，而不是覆盖 |
| 语义 | 独立概率 → 实质是"额外" |
| 类证据 | `ImmersiveEngineering-1.20.1-10.2.0-183.jar` → `api/crafting/IERecipeTypes.class`（`MINERAL_MIX` 注册为 RecipeType）、`api/excavator/MineralMix.class`（`getRandomOre` 的累积循环） |

> **2026-09-18 订正**：原文标「待确认」的这条已查清 —— **是数据包**，且 `MineralMixBuilder`/`MineralMixSerializer` 只在 Java 侧（CraftTweaker 未装），KubeJS 加矿脉的唯一途径就是写数据包 JSON。

### 2.5 IU 量子采石场（数据层有路径但概率不可调 → 实现走 mixin）

| 项 | 内容 |
|---|---|
| 机器类 | `com.denfop.blockentity.mechanism.quarry.BlockEntityBaseQuantumQuarry`（`.../BlockEntityAdvQuantumQuarry`、`BlockEntityImpQuantumQuarry`、`BlockEntityPerQuantumQuarry`）；另有 `BlockEntityQuarryVein`（矿脉机器） |
| 产出机制 | 按区块向 **IU 矿脉系统**查矿脉：`(ChunkPos) → VeinBase`；产出走 `com.denfop.api.recipe.InventoryOutput`；概率由配置键 **`base_quantum_quarry_chance`** 控制 |
| 矿脉 API | `com.denfop.api.vein.common.{Vein, VeinBase, VeinSystem, VeinBaseSystem, Type}` + gas 变体（`api.vein.gas.*`）—— 公开包（`api`） |
| 数据层现状 | IU 的 `data/` 有 584 个 JSON，全是 **`forge:ores` 标签**（`data/forge/tags/blocks/ores/*.json`）；**没有矿脉表** |
| 数据层路径 | **有，但概率不可调**。`industrialupgrade:quantum_quarry` 是正式注册的 recipe type（`Register` 里对 RecipeType 与 RecipeSerializer 各注册一次），schema 为 `{type, recipe_type: default\|furnace\|macerator\|comb_macerator, recipeOperation: addAll\|remove, inputs:[{type: item\|tag, id, amount}]}`。它往 `IUCore.list_quarry` 追加条目，而采石场取用是 `rand.nextInt(main_list.size())` —— **池内均匀 ~1/N**，要凑到 0.1% 得有一千条，不现实 |
| 矿脉 API | `com.denfop.api.vein.common.*` 是公开 Java，但**没有注册入口**，且矿脉只能携带 `Type` + `int meta`，无法表达任意物品 |
| 结论 | **实现走 mixin**，不走数据层 |

**实际实现（2026-09-18）**：`tecend` 新增 `QuantumQuarryFragmentMixin`，`@Redirect` 钩 `BlockEntityBaseQuantumQuarry.updateEntityServer` 里的 `InventoryOutput.add(ItemStack)`，产出成功时按配置概率追加残片。

- **为什么不 `@Inject` 到方法 TAIL**：那个方法**每刻都跑**（第一句就是超类 `BlockEntityInventory.updateEntityServer` 的调用），TAIL 等于每刻掷一次 —— 0.1% × 20/秒，比设计值高三个数量级。真正的产出点是那几次 `outputSlot.add(...)` |
- 字节码里 `InventoryOutput.add` 共 4 处（offset 152 矿脉路线 / 484 通用池·`original` 真·普通矿 / 530 同路线宝石碎片循环 / 552 同路线 `original` 假），一次挖掘只走其中一条 → 一次判定 |
- 概率走配置 `quarry.fragmentChance`，默认 `0.001` |
